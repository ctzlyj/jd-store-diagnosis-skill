# L1 官方 CLI 巡检：诊断口径、行动路由与复检

本文件定义第一层「官方京麦 CLI 只读巡检」（R01–R12）：不依赖浏览器，只要店铺完成过京麦 CLI 授权就能跑。它是三层诊断的第一层——第二层商智/京准通明细（店铺浏览器）与第三层黄金眼补充（无后台权限）见 SKILL.md。哪一层拿不到数据，报告里如实写明，不能编造。

## 规则

| 编号 | 范围与证据 | 判断 |
|---|---|---|
| R01 | full，在售状态103商品完整分页 | 在售商品少于20；这是腾飞经营规则，不是平台处罚规则 |
| R02 | 官方健康列表，低分时补健康详情 | 官方提升项与健康分；缺少证据不视为无问题 |
| R03 | 已读规格的官方价格星级 | 星级不高于3或竞争力bad/avg；不抓竞品、不计算建议改价 |
| R04 | 已读在售商品的官方30天销量 | 明确为0的商品；缺失销量不计0；数量不受明细展示上限影响 |
| R05 | 官方商品30天销量与规格库存 | 有动销商品下库存明确为0的规格；不推断该规格有销量 |
| R06 | full，有效商品违约单 | 排除effectStatus=2；保留严重违规数量与有限明细 |
| R07 | full，最近30天创建、仍待出库的订单 | 按创建时间计算超过24小时；不冒充付款/承诺发货超时 |
| R08 | full，上海时区最近7个完整自然日客服数据 | 官方未回复次数；不读取聊天内容 |
| R09 | full，官方违规商品 | 官方待整改记录；不等同全部下架商品 |
| R10 | full，官方商品申请单 | 驳回或待审核超过24小时；不发起修改申请 |
| R11 | 官方健康诊断中的指定素材因子 | 白底/透图/场景/卖点/标题/视频等官方问题；不是逐槽位覆盖审核 |
| R12 | full，上海时区最近7个完整自然日评价 | degree不高于50；不返回用户身份或评价原文 |

窗口、采集开始/结束时间及数据域覆盖保存在报告内。官方接口没有承诺统一原子快照，因此不同请求之间可能发生业务变动。不要把所有规则结果压成一个无依据的“店铺健康分”。

## 输出约定

- `scope.kind`: sample/full。sample 即使数量碰巧覆盖全部商品，也不执行店铺级检查。
- `scope.wholeStore`: full 且在售商品及规格完整遍历。不是“所有数据域都完整”。
- `status`: complete/sampled/partial。存在未知字段即保留 partial，不用请求成功率替代数据完整率。
- `findings`: 12条诊断记录，包括优先级、状态、统计、原因、证据和数据源引用；不是任务。
- `products`: 已读商品/规格的最小诊断数据；不会包含凭据、买家、地址、客服账号或原始订单。
- `sources`: 每个数据域/商品规格的结果、条数、分页是否完整及采集时间。
- `audit`: 固定 API 名称、时间、请求状态和条数；不存完整请求参数、头、原始响应或上游错误文本。
- `failures`: 安全的来源名与错误码。可取得数据为空、官方指标未返回与接口失败是不同情况。

## 官方返回兼容与回归

1. `success=true`、`paginationData.totalItems=0` 时，京麦可能省略 `data`，也可能返回 null。仅这个有明确零总数的组合视为空列表；缺少总数、对象替代数组等仍报结构错误。空列表价格数据只意味着未获取，不能标为正常。
2. 健康列表100分记录可能不含 `improvementList`，可作为官方无待优化项；低于100分但缺少详情时使用健康详情 GET。健康详情路径参数可以用官方 `healthScoreId`，其值与 `skuId` 一致，不依赖旧的 `healthInfoId` 返回字段。
3. 商品与规格固定排序。规格pageSize=50、productIdList数组；分页检查总数、唯一ID和结束条件。接口返回部分数据后异常时不宣称完整。
4. 业务展示只列部分明细时，问题总数仍按全部已读证据计算，并与抽样范围一起解释。

以上兼容有回归测试；不修改官方 CLI 安装目录或 O2/WebCLI 包。新增响应形态先补失败测试，再修改解析并做同条件只读验证。

## 行动路由（报告行动清单 → 建议承接 Skill）

巡检只读、不派发任务。报告的行动清单为每个触发的问题给出建议承接 Skill；跨 Skill 的统一调度由「黑灯运营智能体」总调度 Skill 负责，本 Skill 不自建任务队列，也不把建议表述为已派发或已授权写入。

| 规则 | 问题 | 建议承接 Skill | 边界 |
|---|---|---|---|
| R01 | 在售商品不足 | jd-jingmai-universal-mover | 整理爆品资料与上架方案；先确认改图与定价策略 |
| R02 | 信息健康/信息分 | jd-material-pop（素材）；jdo-product-update（属性/错挂类目） | 素材审计与维护计划，保留完整规格与审核状态 |

| R06 | 违约单 | jdo-product-price | 取官方详情，先确定整改原因 |

| R11 | 素材待优化 | 短标题/卖点/白底/透图/场景图 → jd-material-pop；主图批量重制 → jd-jingmai-batch-image-refresh；主图视频/长图 → jdo-product-material；电子说明书 → jdo-product-manual | 官方问题因子口径，不替代逐槽位审核 |

## 次日复检（--baseline）

```
node "<skill-root>/scripts/inspection/cli.cjs" scan --profile "<Profile>" --shop-id "<shopId>" --shop-name "<完整店名>" --scope full --baseline "<前一次 report.json>"
```

- 基线与本次必须是同一家店（shopId 一致），否则拒绝比较（BASELINE_SHOP_MISMATCH）。
- 每条规则给出：新增（基线未触发、本次触发）、持续（两次都触发）、已恢复（基线触发、本次已读范围未再触发）、无法判定（本次数据覆盖不完整时不能宣称恢复）。
- 「已恢复」只表示本次已读数据不再触发该规则，不是对整改动作与销量恢复的因果归因。
- 复检与基线一样是只读采集；报告新增「复检对比」一节。

## 首版验收范围

- 自动测试覆盖：身份不匹配、自营拒绝、只读白名单、分页、多商品计数、缺失字段、鉴权/失败率/预算停止、无任务输出、离线计划和非破坏式安装升级。
- 真实只读验收：2026-09-16，单商品及10商品样本完成；10商品样本读取136个规格、30次官方GET，无请求失败。价格星级官方返回空集合，报告如实保留未获取。
- 未进行真实全店扫描、店铺写入、订单/客服全量取数验收、定时运行或非Windows实机验收。不得把自动测试或抽样实测表述为这些场景已经完成。
