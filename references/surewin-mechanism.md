# 京东京准通「稳赚计划」机制、字段口径与提前验价用法

适用：POP 店铺稳赚计划（单品稳赚 / 新品稳赚 / 全店稳赚）的诊断与投放建议。
两类信息严格分开标注：**【官方】= 白皮书原文**；**【推断】= 本地样本观察，需实测验证**。

## 〇、权威来源与抓取方式

官方白皮书：京准通商学院《「稳赚计划」5.0白皮书——100%保收益》，releaseDate 2026-09-23。
页面 `https://jzt.jd.com/school/course/detail?contentId=19372` 是 CSR，直接抓 HTML 只得到「网站加载中…」。
正文走 CMS 接口（匿名可读，无需登录态）：

```
GET https://jzt-api.jd.com/cms/content?contentId=<contentId>
```

返回 `data.txt` 是 Slate 富文本 JSON 字符串，`type=p` 取 `children[].text`，`type=img` 取 `url`。
参数名必须是 `contentId`（传 `id` 报 `code:600 需要id参数`）；该端点只支持 GET。
同页其他数据源：`cms/content/button/list`（POST）、`cms/recommendContentList`、`cms/contentList`。
**结论：京准通商学院任一课程正文都可以用这个方式离线取全文再做规则比对，不必开浏览器。**

## 一、【官方】白皮书核心规则

### 1. 参与资格（商品池实时刷新，商家维度为定向邀约）

| 类型 | 条件 |
|---|---|
| 潜力品（常规稳赚） | 近 30 天订单销量 ≥5 单、累计好评 ≥3 个、价格星级 ≥3 星（俗称 533） |
| 新品稳赚 | SPU 下任一新品 SKU 累计好评 ≥1、价格星级 ≥3 星、在标天数 ≤20 天（绿标/黑标），享 14 天效果保障 |
| 成熟品牌商品 | 533 且近 6 个月 SPU 下 SKU 均未投放广告 |
| 全店稳赚 | 入驻京准通 180 天内 POP 新商（非 O2O、非采销虚拟金、非自营），店内至少 1 个 SKU 达 533，且不同时投放其他产品线或全站营销新品&单品计划 |

### 2. 账户与计划设置（需同时满足，否则不赔）

- 账户限时消耗 **99 元** 即享 100% 成本保效赔付。
- 仅支持**目标成交投产比**出价方式，不能切换出价方式，不支持一键起量；自动暂停/自动降预算/自动降出价等自动化规则自动失效。
- **目标成交投产比设置值需 ≤「稳赚计划投产比最高建议值」**（QA 复述为「投产比设置需低于稳赚投产比建议值」）。
- 活动期内每日最多修改目标投产比 **3 次**。
- 计划需保持投放 **7 天以上**且持续投放，不可暂停或删除；退出/停止后进入 **7 日冷冻期**。
- 保障以 **SPU 粒度**生效，同 SPU 下非新品标商品同样享受。

### 3. 周期与赔付发放

- **28 天为一个投放周期**，期满需重新创建计划；资格按周期刷新，仍是邀约制。
- **每 7 天赔付一次，T+2 自动核算（第 9 天到账，以实际为准）。**
- 未发放赔付的原因：投产比符合预期，或**计划消耗不满足消耗门槛**。
- 赔付为**站内红包**，与现金 1:1 消耗，**有效期 30 天**，可用于新快车/全站营销/京准调研/门店推广。
- 查看路径：京准通首页-财务账户-财务管理-红包-查看详情；计划侧看【稳赚保】标签。

### 4. 赔付公式（白皮书原文）

```
保障金额 = 现金消耗 − 交易额 / (100% × 汇总目标投产比)
汇总目标投产比 = 总交易额 / 预期消耗金额
预期消耗金额 = Σ( 时段交易额_i / 该时段目标投产比_i )
```

白皮书算例：消耗 500、交易额 3000（1000@ROI10 + 2000@ROI20）→ 预期消耗 200 → 汇总目标 ROI 15 → 实际 6 < 15 → 赔付 500 − 200 = 300。

**由公式直接推出的经营含义（数学恒等，非猜测）：**
保障生效时，`净广告成本 = 现金消耗 − 保障金额 = Σ(时段GMV_i / 目标ROI_i)`，
即 **有效广告费率 = 1 / 目标投产比**，与系统实际花了多少钱无关。
所以「100% 保 ROI」保的是**广告费率上限**，不是「保不亏」：

> **只有当商品毛利率 > 1 / 可享保障的最高目标 ROI 时，稳赚才是「保赚」；否则它保的是「亏损上限」。**

同时必须提醒商家：赔付是 30 天有效的站内红包，**只有持续投放才等价于现金**；停投等于放弃已产生的赔付价值。

### 5. 【官方】建议投产比是怎么定出来的

> 「系统会参考**商品历史数据**，并参考**商品所在价格带与三级类目的行业平均投产数据**后动态调整推荐投产比。」

实时动态 ROI：首建计划或连续 7 天投放积累数据、实际达成目标投产，**每 7 天刷新一次建议值**；新品稳赚达成 533 后标识切换为「稳赚」，「有机会按系统建议**上调** ROI 保障」。
→ 稳定达成目标 ROI 会让下一周期的保障线上移，广告费率进一步下降，存在**阶梯复利**。

### 6. 【官方】关键词与稳赚的关系（重要纠偏）

- 5.0 升级 3：「支持快车更多场景投放稳赚，以**关键词 tROI 出价**叠加 100% 成本保效」。
- QA：**「稳赚关键词智投模式」与「稳赚常规品模式」互斥**，且标注【即将上线】。
- 关键词智投 = 系统智能推荐精选词包，**商家只能在系统推荐范围内添加和修改**。

→ 当前阶段**无法自行加词来抬高稳赚 ROI**；稳赚只能设日预算与目标投产比。
关键词准备工作的正确定位：(a) 等关键词智投上线后从系统词包里快速取舍的候选池；(b) 单品稳赚之外并行的独立快车计划（注意「全店稳赚」明确不可同时投其他产品线，单品稳赚无此表述，仍以账户实际校验为准）。

### 7. 其他官方口径

- 订单统计：同快车-全站智能推广，**广告撬动的直接 + 间接订单**（口径比点击归因宽，利于达成目标 ROI）。
- 同时满足常规稳赚与新商全店稳赚：有潜力款 → 潜力款投单品稳赚 + 另建全店稳赚；无潜力款 → 先投全店稳赚，再筛转化效率优的品投单品稳赚。

## 二、接口字段 ↔ 白皮书规则的对应

`POST /dspad/bidding/suggest` 的 `swaBiddingSuggestList[]` 每个 SPU 返回：

| 字段 | 含义 | 依据 |
|---|---|---|
| `recommendBidList[].price` | 三档**系统建议目标投产比**（level 1/2/3，`selectFlag=true` 的是「荐」档）。**不是 CPC 点击出价。** | 前端传入目标投产比编辑器 |
| `topPriceTroi` | 前端参与校验用的**可填上限**（「投产比需≤X 可参与稳赚」）。是输入框边界。 | 前端校验逻辑 |
| `refundLimitPrice` | **【推断】即白皮书所说的「稳赚计划投产比最高建议值」**，也就是**享受赔付保障要求的目标 ROI 上限** | 见下 |
| `costThreshold`（`/dspad/sure/win/spu/cost/threshold`） | **每轮（7 天）累计消耗门槛**，低于它不发赔付 | 白皮书「计划消耗不满足消耗门槛」 |
| `bottomPrice` | 0.01，下限占位 | — |

### `refundLimitPrice` 的推断链（转述时必须保留「推断」二字）

1. 本样本 **30/30 个 SPU** 满足 `refundLimitPrice == max(recommendBidList[].price)`，即恒等于第三档（最高）建议值。
2. 白皮书设置要求写明：「目标成交投产比设置值需 ≤ 稳赚计划投产比**最高建议值**」。
3. 字段名直译即「赔付限制值」。
4. 每个样本都有 `refundLimitPrice < topPriceTroi`（例：1.4 < 2.5、2.1 < 2.9）。

→ **【推断】`topPriceTroi` 只是输入框能填到的上限，`refundLimitPrice` 才是「填到多少还能享受赔付」的线。把目标 ROI 设到 `topPriceTroi` 很可能填得进去却丧失保障资格。**
→ 给商家的稳妥建议：**目标投产比设为 `refundLimitPrice`（= 最高建议档），不要设到 `topPriceTroi`。**
→ 零成本验证方式：在创建页把目标 ROI 填到 `topPriceTroi` 观察是否仍出现【稳赚保】标签/保障提示，再改回（每日可改 3 次）；或第 9 天核对红包到账。

## 三、本地样本观察（两店 30 SPU，同日截面，脱敏）

- **同一价格 + 同一三级类目的商品，跨店返回完全相同的 `topPriceTroi` / `refundLimitPrice` / `costThreshold`。**
  这与白皮书「价格带 + 三级类目行业平均投产」口径吻合；对**零成交、零广告历史**的品，商品历史数据的影响接近于 0。
- 样本自然分成两簇，簇内价格-保障线单调，簇间同价不同值 → 即三级类目不同：
  - 类目甲（本样本 12 品）：价格 ≤40.8 → 保障线 1.4；41.8~56.8 → 1.6；70.8 → 1.7；77.8 → 1.8；85.8 → 1.9
  - 类目乙（本样本 5 品）：14.8 → 1.4；24.8 → 1.6；33.8 → 1.7
- **存在清晰的跳档临界价**：类目甲在 40.8 与 41.8 之间保障线由 1.4 跳到 1.6，
  对应有效广告费率由 1/1.4 = 71.4% 降到 1/1.6 = 62.5%，**1 元定价差 ≈ 8.9 个点的保底广告费率**。
- 第一档建议值在 30/30 样本中恒为 **1.1**（常数，无个性化信息量）；真正随商品变化的是第 2、3 档。
- `costThreshold ≈ 2.0~2.5 × (价格 / refundLimitPrice)`，粗略等于「按保障 ROI 跑出约 2~2.5 单 GMV 所需的消耗」。已获资格的品系数更高（约 2.8~3.7×）。**仅为本样本回归观察，不是公式。**
- 已获资格 vs 同类目同价位未获资格的品对比（当日截面）：资格品 `topPriceTroi` **下降**、`costThreshold` **上升**；其中成交较好的那个 `refundLimitPrice` 高于同价位无成交品（1.6~1.9 → 2.1）。
  → 【推断】未获资格品的 `topPriceTroi` 更像「类目价格带的理论上限」，获资格后才收敛为该商品的实际可填上限。
- 样本中 30/30 商品 `stars=4`（价格星级已达标），绝大多数 `saleVolumeStr=0`，即**卡资格的唯一短板通常是「近 30 天 ≥5 单」**。

## 四、提前验价：把接口变成选品与定价武器

核心事实：`bidding/suggest` + `cost/threshold` 对**尚未获得稳赚资格的 SPU 同样返回**保障线与门槛。
别人要等通栏弹窗才看得到一个品的数字，我们可以一次拿到全店每个 SPU 的「未来保障线 + 入场门槛」。

### 用法 1：全店保障线地图（每周跑一次）

`goodsInsight/sku/list` `requestType=1` 拉全量候选（含无资格），`requestType=80` 拉**当前真正有资格**的 SPU；
再批量 `bidding/suggest` + `cost/threshold`，产出表：
`SPU | 价格 | stars | 近30天销量 | 保障线 refundLimitPrice | 保底广告费率 1/refundLimitPrice | 每轮门槛 costThreshold | 门槛/价格 | 是否有资格`

### 用法 2：毛利率闸门（先筛掉「保亏」的品）

对每个 SPU 计算 `保底广告费率 = 1 / refundLimitPrice`，与商品毛利率比对：

- 毛利率 **>** 保底广告费率 → 值得投，赔付把它锁成确定性生意；
- 毛利率 **<** 保底广告费率 → 即使拿满赔付仍是亏损，只是亏损被封顶。**这类品不该因为「有稳赚资格」就投。**

### 用法 3：定价台阶扫描（真正的「提前验价」）

`suggest` 不接受自定义价格入参，服务端按商品现价计算。所以做法是：

1. 用店内同三级类目、不同价位的现有 SPU 做散点，拟合出该类目的「价格 → 保障线」台阶表（**零成本、不改价**）；
2. 找出卡在台阶下沿的商品（例：类目甲 40.8 的品，只差 1 元就能从 1.4 跳到 1.6）；
3. 小幅提价越过临界点后 **24h 内重跑接口复验**保障线是否真的跳档。

约束：提价不得压低价格星级（需 ≥3 星，`goodsInsight/sku/list` 的 `stars` 可监控），也不得违反活动/价保规则；改价属于商家决策，必须由用户确认后执行，Skill 不代改价。

### 用法 4：定向养资格队列

对**尚未达 533**的品，按 `refundLimitPrice` 高、`costThreshold/价格` 低排序，选 Top N 优先补足「近 30 天 5 单 + 3 好评」（走自然动销、站内活动、特价热卖/秒杀/超补等白皮书提到的频道，**不得刷单**）。
提前知道哪个品将来保障线最高，就知道该先养哪个 —— 这是接口最不可替代的价值。

### 用法 5：每 7 天刷新哨兵

白皮书说建议值每 7 天刷新且达成目标有机会上调；后台每天只能改 3 次目标 ROI。
把 probe 设成周期任务，在刷新日第一时间读到新的 `refundLimitPrice` 并把目标 ROI 抬到新线，吃满阶梯复利。

### 用法 6：预算与门槛护栏（防止「设高 ROI 反而拿不到赔付」）

目标 ROI 设得高 → 系统压量 → 7 天消耗可能跑不过 `costThreshold` → **本轮零赔付**。这是平台的对冲机制。
执行规则：

- 日预算下限 ≈ `costThreshold / 7 × 2`（留足冗余）；日预算是上限不是消耗保证。
- 第 4 天检查累计消耗：若 `< costThreshold × 0.5`，当天下调目标 ROI 一档（用掉每日 3 次修改额度中的 1 次），优先保证过门槛。
- 计划连续开满 7 天以上，不暂停、不删除、不开一键起量、不挂自动化规则。
- 28 天周期结束后重新建计划，并在建计划前重跑一次 probe 取最新保障线。

## 五、采集接口与操作约束

`scripts/surewin-probe.js` 已封装下列调用（须 9224 店铺档浏览器已登录京准通）。
公共请求头：`loginMode: 0`、`siteId: 0`、`language: zh_CN`、`credentials: include`。

- SPU 列表：`POST /goodsInsight/sku/list`（`requestType=1` 全量候选，`requestType=80` 当前有资格）。
- 建议与上限：`POST /dspad/bidding/suggest`，读 `swaBiddingSuggestList[]`。
- 每轮门槛：`POST /dspad/sure/win/spu/cost/threshold`，**必须带同一会话 suggest 返回的 `ext.traceId`**，不可复用旧值。
- 预算建议：`POST /dspad/common/suggest/campaign/budget`；账户活动态：`POST /dspad/sure/win/activity/info`。
- 白皮书正文：`GET https://jzt-api.jd.com/cms/content?contentId=19372`（匿名）。

红线：复用已授权登录态和受控后台页，不干扰用户工作浏览器；Cookie、Token、账号原始响应不入 Git/日志/报告；不代用户创建计划、充值、改价、刷单；写入结果不明先回查再决定是否重试。
